1. Introduction

1.1 Purpose

This SRS defines a teaching simulator for railway reservations with a small, rule-driven disruption 
refund advisor. It is the common baseline for implementation, tests, project report and viva. Tier 1 
(Java) and Tier 2 (MySQL) must work independently and implement the same domain rules.

1.2 Product summary

The reservation engine models trains, dated journeys, seat classes, bookings, unique PNRs, 
cancellations, waitlists and promotion. It demonstrates why concurrent booking requests can over-
allocate a last seat in an unsafe implementation and how a corrected implementation prevents that 
outcome.

The refund advisor evaluates a disruption case using explicitly supplied event records and an effective-
dated, source-referenced rule. It returns an outcome, reason codes, the selected rule/version, deadline 
information and a simulated refund amount. Java and MySQL evaluate the same deterministic fixtures 
independently; a parity checker compares their outputs.

3.2 Business rules
















BR-01: PNR is unique and never reused.
BR-02: one booking holds one seat. A group reference can join multiple independent bookings.
BR-03: a passenger may have at most one CONFIRMED booking per journey, across all seat classes. 
WAITLISTED bookings in other classes may remain as fallbacks.
BR-04: waitlist order is earliest booking timestamp first, then booking ID as a deterministic tie-break.
BR-05: when no seat is available, a valid request becomes WAITLISTED; this is a normal outcome, not an 
exception.
BR-06: a CANCELLED booking is terminal. Re-booking creates a new booking and PNR.
BR-07: cancelling a CONFIRMED booking releases exactly one seat and makes at most one attempt to 
promote the earliest eligible waiter in that journey class. Cancelling a WAITLISTED booking frees no 
seat.
BR-08: fares are non-negative and depend on seat class.
BR-09: promotion skips a passenger who already has a confirmed booking on the same journey in 
another class; it must not mutate an ineligible waitlist entry.
BR-10: booking status and seat/waitlist/allocation tables are changed only through controlled Java 
service operations or the approved MySQL procedures.

3.4 Required lock order

Critical correction from v0.1

Locking only JOURNEY_CLASS cannot protect BR-03, because two concurrent requests can lock different 
classes for the same journey. A common JOURNEY row is therefore the first serialization/lock anchor; the 
relevant JOURNEY_CLASS row is locked second. All booking, cancellation and promotion operations use the 
same documented order.

Revised review draft • 24 October 2026   |   Page 6

1. Begin a MySQL transaction. The first data-access statement must be a locking read (SELECT ... FOR 

UPDATE) of the JOURNEY parent row for the target journey. No plain availability/count read may occur 
first.

2. Lock the affected JOURNEY_CLASS row next. When multiple rows are needed, lock them in deterministic 

key order; do not acquire a class lock before the parent journey lock.

3. While these locks are held, validate immutable booking route/class identifiers, status, passenger 

journey-level confirmed status and available seats; then insert/change booking, allocation or waitlist 
rows.

4. Write audit rows in the same transaction and commit. On any error, roll back the whole operation. 

Deadlocks/lock timeouts are recorded as failed attempts and may be retried by the caller; the retry must 
not duplicate the logical booking.

For cancellation, the procedure receives booking ID plus expected immutable journey/class identifiers 
(or an equivalent safe lookup form). It locks JOURNEY, then JOURNEY_CLASS, then validates that the 
booking really belongs to those identifiers. A mismatched identifier is rejected without mutation. The 
pre-lock lookup, if used by a caller to discover immutable identifiers, is not used to determine 
availability or make a capacity decision.

5.2 Scope and rule-source requirements



The advisor accepts a case only for a CONFIRMED booking with ticket_type = SIMULATED_E_TICKET. 
Waitlisted, RAC, partial-confirmed, party/family PNR, Tatkal and i-ticket cases are unsupported and must 
be rejected with an explicit unsupported-scope reason, not guessed.

 No live train-status or ticket data is read. Case events are simulated records and use source labels such 











as SIMULATED_OFFICIAL and PASSENGER_REPORTED. SIMULATED_OFFICIAL denotes a trusted source 
in a test fixture; it does not mean that the system queried Indian Railways.
Every REFUND_RULE version contains official source URL, source title/section, source_checked_on, 
verification status, ticket scope, threshold, deadline basis and refund basis. A rule cannot be marked 
verified unless its source details and review date are present.
An unverified rule must return UNRESOLVED with RULE_SOURCE_UNVERIFIED; it cannot produce 
ELIGIBLE or NOT_ELIGIBLE. Test fixtures may explicitly mark a source-reviewed synthetic rule as 
verified for deterministic evaluation.
Effective intervals use [effective_from, effective_to); effective_to may be NULL for an open interval. 
Overlapping intervals for the same rule family are rejected by a controlled rule-maintenance procedure.
Rule applicability time and evaluation time are different fields. The fixture supplies 
policy_applicability_time explicitly; for the initial rule set it defaults to the modeled scheduled departure 
at the boarding/commencement station. This is a documented implementation assumption and must be 
checked against the source when publishing each rule. Evaluation never uses the system wall clock.
Case output contains the selected rule ID/version, outcome, normalized reason-code set, warnings, 
deadline timestamp or deadline basis, simulated refund amount, required filing action (if any), and the 
mandatory disclaimer.

9.3 Parity contract

The parity runner compares canonical values, not human prose alone. Required fields: outcome; 
sorted reason-code set; sorted warning set; selected rule ID/version; policy-applicability timestamp; 
deadline timestamp/basis; action-required code; currency; and amount to two decimals. When they 
disagree, emit PARITY_MISMATCH with field-level difference. A parity pass does not prove the policy 
itself is correct; it proves both implementations agree with the fixture oracle.
